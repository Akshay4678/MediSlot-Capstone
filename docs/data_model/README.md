# MediSlot data model (SCHEMA_VERSION 3)

The RDS schema in `application/database/schema.sql` follows the project ER diagram
(`MediSlot_Complete_ERD_updated.drawio`). Column names, relationships and the placement of
`MATERIALISED_SLOTS` in RDS are exactly as drawn, with the deliberate differences below. Please
update the ER diagram to match before the design review.

## Differences from the ER picture (and why)

| ER diagram | Implementation | Reason |
|---|---|---|
| `BIGINT` ids | `CHAR(36)` UUIDs generated by the app | The id is also the JWT `sub` claim and appears in DynamoDB keys and slot ids; UUIDs avoid a central counter. |
| `CONSULTATION_TYPES` has no `doctor_id` (no DOCTORS -> CONSULTATION_TYPES line) | `doctor_id` FK added; unique `(doctor_id, type_name)` | The brief says a doctor defines and edits *their own* types and fees. Without an owner column the ownership check cannot be enforced. **Add the DOCTORS -> CONSULTATION_TYPES ("offers") line to the ER.** |
| `MATERIALISED_SLOTS` has `date`, `start_time`, `end_time` strings | `date` DATE, `start_time`/`end_time` TIME (doctor-local) **plus** `start_utc`, `end_utc`, `timezone` | The brief requires slot times stored in UTC with the originating timezone recorded, and DST-correct materialisation. |
| `TOKEN_ACTIVELIST`: `jti (PK)` | Partition key is `user_id`; `jti` is an attribute | One active access token per user: writing the user's row *replaces* the previous token atomically and is strongly consistent. With `jti` as the key, finding the old token needs an eventually-consistent index, so two tokens could be briefly valid. Update the ER box to `user_id (PK)`, `jti`, `expires_at`, `ttl`. |
| `REFRESH_TOKENS` (no key shown) | Partition key `token_hash`, GSI `user_id-index`, TTL on `expires_at` | Lookup by hash on refresh; the GSI lets logout delete every refresh token of a user. |

## Slot materialisation (how the 30-day window is built)

* **CONSULTATION_TYPES** = what is offered (fixed duration from SSM, fee).
* **AVAILABILITY_PATTERNS** = weekly template in the doctor's local time: ISO weekday, `start_time`,
  `end_time`, consultation type and `capacity` (1; 2-10 only for Health Camp Sessions).
  The doctor's IANA timezone lives on `DOCTORS.timezone`.
* A daily EventBridge Scheduler job (and every availability / blackout / timezone change) creates one
  `MATERIALISED_SLOTS` row per slot for the next 30 local days. `slot_id =
  doctor_id#availability_id#startUTC`, written with `INSERT IGNORE`, so running it twice creates nothing new.
* `MATERIALISED_SLOTS` is derived, rebuildable data. 1 doctor x 6 slots/day x 30 days = 180 rows.

## Worked example across a daylight-saving change (also a unit test)

Doctor in `America/New_York`, pattern *every weekday 09:00-17:00, 60-minute slots*. US clocks go back on
Sunday 1 Nov 2026.

| Local date | Offset | First slot (local) | First slot (stored UTC) | Last slot (local -> UTC) |
|---|---|---|---|---|
| Sat 31 Oct 2026 | EDT, UTC-4 | 09:00 | 13:00Z | 16:00 -> 20:00Z |
| Mon 2 Nov 2026 | EST, UTC-5 | 09:00 | 14:00Z | 16:00 -> 21:00Z |

Local wall-clock times are stepped in local time and converted with the IANA zone, so the doctor's
09:00-17:00 never moves. A local time that does not exist (spring-forward gap, e.g. 02:30 on 8 Mar 2026)
is skipped instead of being shifted.

## Schema upgrades

`init_schema.py` records `SCHEMA_VERSION` in `schema_meta`. A Milestone 2 (pre-ER) database is rebuilt
once - tables are dropped and recreated - but **only when `ALLOW_SCHEMA_REBUILD=true`**, which the pipeline
sets for `dev` only. Re-running on the current version is a no-op.
