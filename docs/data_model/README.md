# MediSlot data model (SCHEMA_VERSION 5)

The RDS schema in `application/database/schema.sql` follows the project ER diagram
(`MediSlot_Complete_ERD_updated.drawio`). Column names, relationships and the placement of
`MATERIALISED_SLOTS` in RDS are exactly as drawn, with the deliberate differences below. Please
update the ER diagram to match before the design review.

## Differences from the ER picture (and why)

| ER diagram | Implementation | Reason |
|---|---|---|
| `BIGINT` ids | `CHAR(36)` UUIDs generated by the app | The id is also the JWT `sub` claim and appears in DynamoDB keys and slot ids; UUIDs avoid a central counter. |
| One `CONSULTATION_TYPES` table | Two tables: `CONSULTATION_TYPES` (fixed catalogue: `type_name` unique, `duration_minutes`) and `DOCTOR_CONSULTATION_TYPES` (`doctor_id`, `consultation_type_id`, `fee`; unique per doctor and type) | Each doctor sets their own fee per type, while names and durations are fixed by the platform rules. Splitting them keeps the fixed facts in one place. `AVAILABILITY_PATTERNS`, `MATERIALISED_SLOTS` and `APPOINTMENTS` keep `consultation_type_id` (the catalogue id) and reference the pair `(doctor_id, consultation_type_id)`, so a doctor can only schedule or be booked for a type they offer. Drawn in the ER as DOCTORS -> DOCTOR_CONSULTATION_TYPES ("offers") and CONSULTATION_TYPES -> DOCTOR_CONSULTATION_TYPES. |
| `MATERIALISED_SLOTS` has `date`, `start_time`, `end_time` strings | `date` DATE, `start_time`/`end_time` TIME (doctor-local) **plus** `start_utc`, `end_utc`, `timezone` | The brief requires slot times stored in UTC with the originating timezone recorded. |
| `TOKEN_ACTIVELIST`: `jti (PK)` | Partition key is `user_id`; `jti` is an attribute | One active access token per user: writing the user's row *replaces* the previous token atomically and is strongly consistent. With `jti` as the key, finding the old token needs an eventually-consistent index, so two tokens could be briefly valid. Update the ER box to `user_id (PK)`, `jti`, `expires_at`, `ttl`. |
| `REFRESH_TOKENS` (no key shown) | Partition key `token_hash`, GSI `user_id-index`, TTL on `expires_at` | Lookup by hash on refresh; the GSI lets logout delete every refresh token of a user. |

## Slot materialisation (how the 30-day window is built)

* **CONSULTATION_TYPES** = the fixed catalogue (name and duration from SSM). **DOCTOR_CONSULTATION_TYPES** = what each doctor offers and their own fee.
* **AVAILABILITY_PATTERNS** = weekly template in the doctor's local time: ISO weekday, `start_time`,
  `end_time`, consultation type and `capacity` (1; 2-10 only for Health Camp Sessions).
  The doctor's IANA timezone lives on `DOCTORS.timezone`.
* A daily EventBridge Scheduler job (and every availability / blackout / timezone change) creates one
  `MATERIALISED_SLOTS` row per slot for the next 30 local days. `slot_id =
  doctor_id#availability_id#startUTC`, written with `INSERT IGNORE`, so running it twice creates nothing new.
* `MATERIALISED_SLOTS` is derived, rebuildable data. 1 doctor x 6 slots/day x 30 days = 180 rows.

## Timezone design note

* `DOCTORS.timezone` holds the doctor's home timezone as an IANA identifier (default `Asia/Kolkata`).
* Availability patterns are stored as local times (`start_time`, `end_time`) in that timezone.
* Every materialised slot stores the local `date`/`start_time`/`end_time`, the UTC instants
  `start_utc`/`end_utc`, and the originating `timezone`.
* Example: Dr. Rao (`Asia/Kolkata`, UTC+05:30) has Monday 09:00-12:00, Standard Consult (30 min). Monday
  2026-11-02 gets six slots, 09:00 ... 11:30 local, stored as 03:30Z ... 06:00Z.
* Daylight-saving transitions are out of scope for this project (agreed with the mentor): use a timezone without
  daylight saving.

## Schema upgrades

`init_schema.py` records `SCHEMA_VERSION` in `schema_meta`. A Milestone 2 (pre-ER) database is rebuilt
once - tables are dropped and recreated - but **only when `ALLOW_SCHEMA_REBUILD=true`**, which the pipeline
sets for `dev` only. Re-running on the current version is a no-op.

## Migration 4 -> 5 (consultation types split)
`init_schema.py` upgrades a version 4 database without losing data: it drops the old foreign keys and renames the old
table to `consultation_types_v4`, lets `schema.sql` create the new tables, copies every old row into the catalogue (one per
type name) and into `doctor_consultation_types` (keeping each doctor's fee), repoints `consultation_type_id` in the three child
tables to the catalogue id, adds the `(doctor_id, consultation_type_id)` foreign keys and finally drops `consultation_types_v4`.
Every step checks the current state first, so a failed run can be repeated.
